# Login and private NAS runtime

## Rationale and first release boundary

A crew member must be able to return to the same Project and Shoots from another browser without putting private data in public source. This first release provides NAS-provisioned local accounts, multiple private projects per account, schedule/shoot/member/equipment/camera/reference state, PDF script preview and original download, and private reference images. Public signup and shared workspaces remain deferred. Administrators can invite new members through capacity-limited registration links. External ChatGPT access uses the scoped OAuth/MCP boundary described below; in-app API-key AI is not provided. A new account starts empty. Existing browser demo edits are never silently imported.

## User flow and reusable modules

Login → project settings → add Shoots and schedule → attach PDF scripts / reference images → changes persist on NAS → logout. The existing visual shell is retained. `src/app/session.js` owns login, `src/integrations/api.js` owns transport and revision handling, and `src/domain/workspace.js` owns the shared validation contract. `server/auth.js`, `server/store.js`, and `server/index.js` isolate passwords, database access, and HTTP routing. Further page extraction should follow ARCHITECTURE.md; new infrastructure does not belong in app.js.

The legacy `contents` storage key is an internal compatibility name for Shoot. User-facing language is Project → Shoot. Cameras and reference groups remain reusable entities. Scripts retain original PDF bytes and are linked by file ID. This first version supports PDF source documents; other document formats need a separate safe conversion boundary.

## Security

Passwords use asynchronously derived scrypt hashes with random salts. Account provisioning/reset runs inside the NAS container, receives a password on stdin, and invalidates that user's sessions. No bootstrap endpoint or public registration exists. Invitation-based registration is described below. Sessions contain 256 random bits; only SHA-256 token digests are stored. Cookies are Secure, HttpOnly, SameSite=Strict and expire after 12 hours. Cookie-authenticated mutating requests require the configured exact Origin. OAuth back-channel and MCP requests use their dedicated validation and authentication. Login has account/global budgets and a concurrent hashing limit without trusting forwarded IP headers.

Every data/file query checks the authenticated account. Workspace writes validate structure, safe identifiers, references and ownership; revisions prevent silent overwrites from two tabs. Private bytes live in SQLite, never a public static directory. Files are limited to 10 MiB each, 250 MiB per account, and signature-checked PDF/PNG/JPEG/WebP. SVG/HTML are refused. File responses are sandboxed with nosniff; downloads preserve the original. CSP blocks inline scripts. No request bodies, passwords or filenames are logged.

The server explicitly serves only index.html and src JS/CSS. It never serves repository configuration, runtime databases or server source. SQLite WAL storage is in a named NAS volume. The container runs as an unprivileged user with a read-only root filesystem, dropped capabilities, no published host port, and access through the existing cloudflared network.

## Operational limits

This is a small trusted-team deployment, not a general public hosting service. Login budgets are process-local and reset on restart. Storage uses synchronous SQLite operations with bounded payloads. Files replaced in the UI remain in storage; deleting unused attachments and quota management UI are future work. Account workspaces are isolated, not collaborative. Project snapshots stay in the same private account workspace and share its revision check and quota. Older single-project data is retained without destructive database migrations. An old application image can display only the active project and may reject saving the newer multi-project payload; roll forward to this version to resume editing. Backups are required; the app does not encrypt the NAS disk. NAS administrators control the runtime database. See NAS_DEPLOYMENT.md for deployment and verification.

## Administrator and invitation registration
The first successful login becomes the site administrator. On upgrade, the earliest retained session identifies that owner; if no sessions remain, the first provisioned account is used. The selected account ID is stored once in private `site_settings` and cannot be changed by signup payloads. CLI-provisioned accounts do not automatically gain administrator status.

Settings exposes invitation creation/list/revocation only to the administrator. Each link contains 256 random bits, expires after the selected 12, 24 or 48 hours, and permits the selected positive integer capacity or unlimited signups. Existing links retain a capacity of one. Only a hash of its token is stored. The raw link is shown once and uses a URL fragment, which the browser removes before submission; it does not enter server request URLs or referrers. The administrator shares links directly; Studio does not send email. A maximum of 20 active invitations bounds invitation creation.

Signup checks exact Origin, token validity, password policy, username format and case-insensitive uniqueness. Consumption and user creation are committed in one transaction after hashing, with a second expiry/revocation check so concurrent signup or revocation cannot reuse a link. Rate/concurrency budgets bound password hashing. Signup never assigns administrator privileges or shares the administrator's projects. Registration requires a signed-out browser (or a private window), avoiding confusion with an existing account session. The new user signs in separately and receives an empty private workspace. Revoking an available invitation does not delete an account that already joined.


## External ChatGPT connection
`server/oauth.js` implements a private OAuth authorization-code/PKCE S256 boundary with dynamic public/confidential client registration and protected-resource/authorization-server discovery. Registered callback URLs must use HTTPS on the exact ChatGPT hosts `chatgpt.com` or `chat.openai.com`, with no userinfo, fragment or alternate port; actual redirects must exactly match registration. The MCP resource is exactly APP_ORIGIN + `/mcp`. Pending consent expires after 10 minutes; authorization codes are single-use with a two-minute lifetime. Studio login is required to consent. Read is required; write is separately opt-in. Denial redirects with an OAuth error, never a code.

Access tokens last one hour; rotating refresh tokens last up to 30 days from grant creation. Only token/code hashes are stored. Token resource/client/PKCE are checked; revocation immediately blocks tokens and proposals. Settings lists only the current user's connections and can revoke them. No provider credentials or OpenAI API requests are needed. Cookie sessions cannot authenticate MCP, and bearer credentials cannot access the ordinary app API or attachment bytes. OAuth codes are transient callback parameters, not browser storage. Do not log authorization headers, token requests or callback query strings at reverse proxies.

`server/mcp.js` exposes stateless Streamable HTTP JSON-RPC at `/mcp`: initialize, notifications, ping, tools/list and tools/call. GET SSE is not provided (405). Read tools list projects and retrieve one project, excluding settings and file bytes. Write-consented clients can stage up to 20 domain commands, inspect the field changes/impact, obtain user confirmation in ChatGPT, and apply the one-use proposal before its ten-minute expiry. The `confirmed` argument is the client's assertion after ChatGPT's tool/user confirmation, not independent proof of human review. The write tool is marked destructive and is never advertised to read-only grants. Trusted ChatGPT behavior and the user's account consent remain part of the authorization boundary.

Account identity always comes from the grant; project IDs and referenced entities are checked inside that account. All writes use `server/workspace-service.js`, the same structure/file-ownership checks and global revision used by direct UI saves. `src/domain/commands.js` is shared with direct UI creation; layout operations share the existing layout domain module. No arbitrary SQL, code execution, file download, credential mutation, role changes, bulk deletion, shell commands or cross-account reads are exposed. Project content is explicitly labeled untrusted data in server/tool instructions.

Static initialize/ping/tools-list discovery is public so ChatGPT can inspect an app before account connection; it reveals only tool definitions, never project data. Unauthenticated tool calls return an Apps SDK authentication challenge. Expired or invalid bearer tokens still return 401. DCR supports none, client_secret_post and client_secret_basic; confidential client secrets are returned only at registration and stored as hashes. Existing public clients remain valid after the additive migration. The MCP endpoint limits authenticated requests to 90/minute per grant (with a separate bounded public-discovery budget) and bounds input to 128KiB; OAuth registration/pending requests and proposals are bounded. Limits are process-local and reset on restart. This remains a small trusted-team system. For schedules, the impact preview warns that resource/person conflicts are not yet automatically calculated. Attachment text extraction, file uploads through ChatGPT, history/undo and push updates to open browser tabs are not included; refresh Studio after external changes, and revision checks protect against overwriting stale state.

Implementation references: [OpenAI Apps SDK examples](https://github.com/openai/openai-apps-sdk-examples), [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), and [Streamable HTTP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).


## Connection troubleshooting
Administrators can open Settings → external connections → connection diagnostics after retrying app creation. The authenticated `/api/connections/diagnostics` endpoint returns the last 30 protocol outcomes from a maximum of 100 retained events, expiring after 24 hours. Records contain only stage, time, HTTP status, allowlisted error code, allowlisted authentication method, and callback hostnames (no paths, query strings or userinfo). Request/response bodies, client IDs/secrets, authorization codes, tokens, headers, cookies, usernames, project data and file content are never recorded. Events establish whether a request reached Studio; absence alone cannot distinguish a client-side validation failure from an edge/network rejection. Successful metadata or registration events do not prove completion of ChatGPT connection.


## Manual confidential clients
Administrators may generate a manual client in Settings → external connections → manual OAuth setup. This uses an authenticated, exact-Origin checked `/api/connections/clients` route and the same strict callback-host validation as DCR. Up to ten active manual clients are allowed per administrator. The secret is returned once and retained only as a hash; list endpoints never return it. The browser keeps it only in a masked, transient field with copy/clear controls, not in local/session storage or diagnostics.

The external app's manual-client OAuth setting receives this ID/secret; Studio account login and read/write consent remain required. A manual client accepts secret POST or Basic authentication, with PKCE still required; it never accepts public `none` authentication. DCR clients retain their specifically registered authentication method. Revoking a manual client disables future authorization/token exchanges and all associated account grants/proposals. Registration is not evidence of successful connection in the external app.
