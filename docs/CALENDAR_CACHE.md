# Cached calendar display and background refresh

All schedules reuses previously fetched minimal Google event display data after fresh server status and calendar-list permission checks. The first uncached view still needs network reads; this is not zero-latency or offline permission authorization. Metadata failure clears private event data instead of showing unverified cached content.

Cache is memory-only, bounded to24 source/range entries and approximately2MB, with five-minute retention checked on access and each minute. No credentials or event descriptions are cached. A server-issued opaque identity binds the cache to the signed-in Studio account/session and Google subject/connection generation. Keys additionally include calendar ID, exact date range and display timezone. Server checks this identity before and after calendar/event reads. Account/connection change, logout, explicit disconnect, authentication failure, page hide and successful edits clear/invalidate the relevant cache. Calendar permission loss and source visibility changes invalidate affected entries. Late invalidated requests cannot repopulate them.

A cache hit younger than30seconds avoids another event request; status/permissions are still checked. Otherwise cached rows appear while a deduplicated event read runs. Transient event failures may retain a still-bounded cached snapshot, with visible stale/incomplete warnings. Permission errors never fall back to revoked data. Each visible calendar view refreshes about once per minute, and on focus/visibility return at a minimum15second interval. Detached views stop listeners/timers and discard obsolete responses; fast navigation queues only the latest view. Background refresh leaves the toolbar/date/density/sidebar intact, preserves scroll, avoids active text selections, and pauses during event editing. Successful edits invalidate the calendar before refresh.

The top day/week/month, previous/today/next and sidebar controls use matching shared desktop/mobile heights. Existing alignment, source colors/visibility, all-day-first order and event editors remain intact.

Verification uses temporary accounts and mocked providers only. Unit tests cover partition keys, bounds/expiry, minimal fields, dedupe, stale failure and late-response invalidation. Browser checks cover cache hits before delayed event reads, timed automatic refresh, metadata permission loss, reconnect/account switch/disconnect, stale failure notices, dirty editors/edit invalidation, fast view changes, toolbar identity and1440/390/320 heights. No real OAuth grant or calendar is modified.
