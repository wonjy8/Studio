# Cached calendar display and background refresh

All schedules reuses previously fetched minimal Google event display data after fresh server status and calendar-list permission checks. The first uncached view still needs network reads; this is not zero-latency or offline permission authorization. Metadata failure clears private event data instead of showing unverified cached content.

Cache is memory-only, bounded to24 source/range entries and approximately2MB, with five-minute retention checked on access and each minute. No credentials or event descriptions are cached. A server-issued opaque identity binds the cache to the signed-in Studio account/session and Google subject/connection generation. Keys additionally include calendar ID, exact date range and display timezone. Server checks this identity before and after calendar/event reads. Account/connection change, logout, explicit disconnect, authentication failure, page hide and successful edits clear/invalidate the relevant cache. Calendar permission loss and source visibility changes invalidate affected entries. Late invalidated requests cannot repopulate them.

A cache hit younger than30seconds avoids another event request; status/permissions are still checked. Otherwise cached rows appear while a deduplicated event read runs. Transient event failures may retain a still-bounded cached snapshot, with visible stale/incomplete warnings. Permission errors never fall back to revoked data. Each visible calendar view refreshes about once per minute, and on focus/visibility return at a minimum15second interval. Detached views stop listeners/timers and discard obsolete responses; fast navigation queues only the latest view. Background refresh leaves the toolbar/date/density/sidebar intact, preserves scroll, avoids active text selections, and pauses during event editing. Successful edits invalidate the calendar before refresh.

The top day/week/month, previous/today/next and sidebar controls use matching shared desktop/mobile heights. Existing alignment, source colors/visibility, all-day-first order and event editors remain intact.

Verification uses temporary accounts and mocked providers only. Unit tests cover partition keys, bounds/expiry, minimal fields, dedupe, stale failure and late-response invalidation. Browser checks cover cache hits before delayed event reads, timed automatic refresh, metadata permission loss, reconnect/account switch/disconnect, stale failure notices, dirty editors/edit invalidation, fast view changes, toolbar identity and1440/390/320 heights. No real OAuth grant or calendar is modified.

## Reload persistence

The browser now retains a single bounded minimal snapshot in localStorage (schema1, at most24 range/source entries,2MB and five minutes). It is partitioned by Studio account, opaque session/Google connection identity, calendar ID, exact range and timezone. It stores display title, provider IDs/date endpoints/color and bounded completeness warnings; it excludes descriptions, locations, URLs, credentials and arbitrary nested provider fields. Persistence requires Web Locks for atomic cross-tab writes; unsupported browsers remove the old snapshot and use memory only. Unreadable storage uses memory only; snapshot-write quota failures retain valid fresh events in memory without retaining the failed snapshot; oversized sources are returned complete but not cached rather than silently truncated.

A hard reload starts with no private cached DOM. Fresh account/connection status and readable-calendar metadata must succeed before activation/hydration and source pruning. The verified cached snapshot then renders while a forced event refresh runs, even if the saved entry is under30seconds old. Restored entries request refresh=1 so the server also bypasses its event cache. This removes the event-fetch wait, not the required bootstrap/permission-check latency. An offline cold reload cannot validate identity/permissions and therefore hides/purges private cached events; it does not promise offline access. A status accountId mismatch also fails closed, including a login changed in another tab.

Pagehide clears private DOM and memory for BFCache but retains the bounded snapshot for the next verified bootstrap. Explicit logout/disconnect, connection/account change, source visibility changes and401/403/404/409/CALENDAR_NOT_FOUND invalidate persisted data. Cross-tab storage removal/context changes/invalidation signals clear visible private rows regardless of text selection or a retained body-level editor draft. All application snapshot writes and invalidations share one origin-scoped Web Lock. Each invalidation rotates a non-sensitive durable fence, and a pending read must still match that fence under the lock before writing. This prevents a second tab from resurrecting purged data even before it receives its storage notification. A fixed-length fence is reserved before durable reads. Purge frees snapshot space before rotating the fence; if fence replacement still fails, it removes the old fence so old readers fail validation. The fence normally remains after logout without any event/account data. API completion for logout, disconnect and reconnect awaits the durable purge before app-controlled navigation; pagehide alone cannot guarantee completion after an externally forced browser close. Late invalidated reads cannot repopulate the cache. Transient event-read failure may retain a verified bounded snapshot with the existing stale/incomplete warning. Existing connection grants and remote settings are unchanged.

Month rows have an explicit equal track height controlled by calendar density, with each dense event list scrolling inside its cell. Holiday names come only from visible, explicitly designated holiday sources; there is no newly integrated authoritative Korean holiday feed or invented lunar/substitute-date table. Selected range segments have white backgrounds, and all-day surfaces use rounded rectangles. Scoped desktop schedule gutters are reduced; mobile retains the shared gutter.
