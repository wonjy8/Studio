# Calendar display preferences

All schedules keeps its existing month/week/day renderer and list access. Google event names are shown as the actual event title; provider/calendar identity remains in accessible labels/tooltips and the source sidebar. Calendar display colors and visible/hidden choices are browser preferences partitioned by Studio account and stable source ID (`google:<calendar-id>`, `project:<project-id>`, `school:<course-id>`). Same-name calendars remain independent. Google-provided calendar background color is the default; Studio overrides never modify remote calendar colors, subscriptions, events or OAuth grants.

The collapsible right sidebar lists only actual supported sources. Each row has a colored visibility checkbox and a keyboard-accessible menu button; right-click opens the same color/source menu. Changes apply immediately and persist across reloads. Sidebar toggles preserve date, view and current scroll positions; mobile uses a bounded right panel. List markers use the same saved source colors/visibility.

Actual all-day events have filled rounded color chips; timed events retain a transparent background with a small left marker and legible time. Google date/dateTime and exclusive end semantics survive multi-day splitting, including timed overnight segments whose displayed start time can be blank. Foreground is selected against the actual fill luminance. Weekends use a light neutral surface and red dates, while holidays affect date text alone. Today/focus states remain distinct in both themes.

No authoritative public-holiday feed is automatically integrated. A user can explicitly designate a real existing source as a holiday source; only its visible all-day dates receive holiday date styling. Ordinary all-day events and calendar names are never automatically assumed to be public holidays. No lunar/substitute dates are hardcoded or invented.

Calendar vertical density is bounded from65% to250%, with desktop gesture/keyboard decrease/increase/reset. In desktop fine-pointer calendar surfaces, Ctrl-wheel (including browsers delivering trackpad pinch as Ctrl-wheel), Ctrl/Cmd +/-/0 and delivered gesture events change vertical time-slot/month-row height while preserving horizontal geometry. Normal scrolling and editable controls remain native. App-level browser-delivered zoom gestures are prevented only on supported desktop app surfaces, excluding text inputs, editable content and local canvas zoom. Browser-menu/OS accessibility zoom cannot be guaranteed blocked, and no browser/security settings are changed. Mobile behavior is preserved.

Verification uses synthetic local provider/account fixtures: `tests/calendar-preferences.test.js`, `tools/qa-calendar-sources.mjs` and existing calendar/Google UI regressions. Screenshot downloads remain blocked by the executor's403 proxy; no pixel matching to supplied images is claimed. Local screenshots and browser geometry verify desktop/mobile overflow, light/dark colors, source isolation and supported zoom behavior.

The toolbar offers day/week/month/year views, previous/today/next navigation, a left Calendar/List switch and an accessible three-line source-sidebar button. Routine refresh and visible density/reset controls are removed; Ctrl-wheel/gestures and Ctrl/Cmd +/-/0 retain vertical density behavior. The functional year grid contains twelve real months with date/event counts and day drill-down. Provider year reads are split into at most90-day requests under the unchanged93-day API constraint, with cross-range event deduplication. Source preferences remain unchanged. The supplied weekly reference image was not accessible; exact visual matching is unverified.

Oversized year source reads (HTTP413) subdivide sequentially down to individual days while keeping successful subranges. Persistently unreadable dates show incomplete counts or a question mark, not a claim of zero events. List view uses its own explicit query range and hides irrelevant calendar period/navigation controls.
